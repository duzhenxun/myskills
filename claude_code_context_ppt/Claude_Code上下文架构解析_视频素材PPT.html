上下文架构解析

这套 PPT 主要讲 Claude Code 如何通过分层压缩、记忆提炼、自动触发和工具减负来管理上下文窗口。

4 压缩层级
L1-L4 核心机制
3 关键能力
  • 先讲四层上下文压缩体系分别负责什么，以及为什么要分层治理。
  • 再讲会话记忆、结构边界锁、阈值控制这些工程实现细节如何保证压缩不失真。
  • 最后落到自动触发、工具结果外置和主动调度，解释上下文窗口为什么需要被精细管理。

内容结构预览：整套 PPT 会依次展开四层压缩、重建机制、自动熔断和工具系统减负。

内容主线

核心问题不是“上下文能不能装下”，而是“哪些信息值得留下、哪些必须被压缩或外置”。

四层上下文压缩总览

Claude Code 通过四层递进机制处理上下文，目标是在不破坏结构的前提下持续减负。

L1 到 L4 不是同一种压缩强度，而是不同阶段的治理策略。 01 / 12

L1 微压缩的核心逻辑

微压缩靠规则裁掉过时的大体积输出，同时尽量保住服务端已缓存的 Prompt 前缀。

这一步的关键不是删得多，而是删得准，不能把缓存命中链条切断。 02 / 12

微压缩的双轨决策与线程隔离

系统会区分缓存仍有效与缓存已过期两种路径，并用线程隔离避免并行 Agent 互相污染上下文。

Cached Microcompact 和 Time-based Microcompact 解决的是不同状态下的回收问题。 03 / 12

L2 会话记忆压缩

第二层不再删消息，而是把杂乱会话提炼成结构化记忆，沉淀到可复用的 MEMORY.md。

会话记忆的价值在于抽取事实、进度和偏好，而不是保留所有聊天细节。 04 / 12

结构边界锁与 API 完整性

裁剪上下文时必须保住 `tool_use` 与 `tool_result` 的配对关系，否则模型调用链会直接失效。

上下文压缩不是字符串裁剪，而是要遵守消息结构约束的精细手术。 05 / 12

Threshold Dials 阈值控制

系统通过 Token 数、消息条数和最大上限三组阈值，决定什么时候截断以及截断到什么程度。

压缩策略不是一次性开关，而是一套可调节的边界旋钮。 06 / 12

L3 完整压缩机制

完整压缩先做深度分析，再把结果汇总成摘要，把冗长对话日志从最终上下文中剥离出去。

重点不是把日志塞进窗口，而是让模型先想清楚，再带着结论继续工作。 07 / 12

完整压缩后的战后重建

压缩完成后，新上下文要靠文件内容、Plan、Skill、MCP 说明和 Agent 列表重新搭起工作现场。

摘要只是桥梁，真正恢复战斗力还要靠一套可重新注入的工作资产。 08 / 12

L4 自动触发与熔断保护

当上下文逼近窗口上限时，系统会自动触发压缩，并用熔断器阻止无意义的重复重试。

自动触发的本质是主动治理资源，而不是等窗口爆满后再被动补救。 09 / 12

子 Agent 递归死锁防御

系统会显式排除某些 fork 出来的子 Agent 触发自动压缩，避免压缩过程中再触发压缩形成无限递归。

工程系统最怕自我调用失控，这一层就是为了防止连锁死锁。 10 / 12

工具系统的上下文减负

面对巨型 `tool_result`，系统用指针替换和外部存储把大块数据搬出主上下文，只留下可引用的摘要入口。

不要让模型吞完整块 JSON，而要让它通过小指针访问真正需要的信息。 11 / 12

核心洞见：主动管理上下文

上下文窗口不是被动容器，而是稀缺资源，关键问题从“能不能塞下”变成“该不该塞进去”。

这套架构背后的工程哲学，是把 Token 管理从装箱问题升级为调度问题。 12 / 12
