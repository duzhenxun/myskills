Oh My OpenAgent / OMO

OMO 的核心：把 OpenCode 变成一支 AI 开发团队

OMO 不是给 OpenCode 加几个命令那么简单。它是在编码工具之上叠了一层编排系统：Sisyphus 做主指挥，Prometheus 先规划，Hephaestus 深度执行，Oracle、Librarian、Explore 等专家并行补位，最后用工具链和验证闭环把任务推进到完成。

从 OMO 开始 看 Team Mode

OMO One-Line Mental Model

入口装好后输入 ultrawork / ulw，让系统自动启动工作流。
主控Sisyphus 负责理解需求、拆任务、分派角色、持续推进。
团队规划、架构、文档、探索、前端、后端、测试等角色并行工作。
工具LSP、AST-Grep、Tmux、MCP、Hashline、Hooks、Skills。
目标不只是回答你，而是把任务做到可交付、可验证、可收尾。

01 / OMO Positioning

OMO 解决的是Agent 工程化问题

单个 Agent 很容易陷入三类问题：需求没问清就开工、上下文越堆越乱、工具不稳定导致改错。OMO 的重点，是把这些问题放到一个多智能体工程系统里解决。

不是 Prompt 包

它是编排层

OMO 关心的是“谁来判断、谁来计划、谁来执行、谁来验证”。模型只是工人，编排才是项目能否完成的关键。

不是单线程助手

它是团队模式

Sisyphus 可以把任务拆给多个专家和 worker，让它们并行跑，主会话保持干净，结果回来再整合。

不是只会聊天

它贴近真实工程

通过 LSP、AST-Grep、MCP、Tmux、Hashline 等工具，OMO 让 Agent 更像在 IDE 和终端里工作，而不是凭记忆改文件。

02 / Discipline Agents

Sisyphus 是老板，其他 Agent 是专业岗位

OMO 的角色设计很清楚：主 Agent 不应该亲自包揽所有脏活累活，而是像技术主管一样判断任务类型，再调动更适合的角色。

Commander

Sisyphus

主指挥官。负责制定计划、分配任务、调度专家团队，并用激进的并行策略推动任务直到完成。它的价值不在“自己写多少代码”，而在让整个系统不迷路、不停摆、不半途而废。

Prometheus战略规划师。动手前先访谈、澄清范围、指出模糊地带，产出更可靠的执行计划。
Hephaestus深度工作者。适合目标明确但执行链很长的任务，会探索代码库模式并端到端推进。
Oracle架构与调试专家。处理复杂推理、技术取舍、故障分析、架构评审。
Librarian文档和检索专家。适合查官方资料、长文本、API 细节和外部上下文。
Explore快速代码探索角色。适合 grep、定位模块、扫代码关系，给主控补充局部地图。

03 / Team Mode

Team Mode 是 OMO 从“子 Agent”升级为真正多 Agent 系统的关键

一个 Agent 可以很快，但一支协调的团队才适合大规模任务。OMO 的 Team Mode 让一个领导 Agent 协调多个按类别专业化的成员，并通过专用 team_* 工具通信。

创建团队

领导 Agent 创建成员，按任务类型分 lane，比如架构、前端、后端、测试、安全。

分发任务

通过 team_create、team_send_message、team_task_create 等工具分配工作。

并行执行

多个成员同时推进，tmux focus + grid 布局能观察每个成员的实时状态。

对抗规划

hyperplan 可以让多个评论者从不同角度撕计划，先暴露风险再动代码。

安全审计

security-research 可以组合漏洞猎手和 PoC 工程师，按实际可利用性校准风险。

04 / OMO Workflow

一次 OMO 任务通常怎么跑

IntentGate

先判断用户真正想要什么，避免只按字面意思执行。

Prometheus

需求不清楚时先访谈、提问、定边界，再产出计划。

Sisyphus

把计划拆成角色和任务，决定哪些专家并行上。

Workers

执行 Agent 用自己的上下文和工具处理代码、文档、测试、审计。

Ralph Loop

对未完成项持续追踪，达不到完成标准就继续修复。

Finish

主控汇总结果、解决冲突、跑验证、收尾并释放临时资源。

一个典型入口

你不需要手动决定谁来做。OMO 的理想体验就是：给目标，系统自己规划、调度、执行、验证。

ulw 给 Next.js 项目加登录认证
ultrawork 修复所有 eslint 警告
/start-work 先访谈并制定计划

05 / Engineering Tools

OMO 真正硬的地方：给 Agent 世界级开发工具

多 Agent 只是组织形式，能不能稳定完成任务，还要看工具层。OMO 把 LSP、AST-Grep、Tmux、MCP、Hashline、Skills、Hooks 这些能力集成进 Agent 工作流。

LSP

IDE 级代码理解

支持重命名、跳转定义、查引用、诊断等能力，让 Agent 不只靠搜索和猜测理解代码。

AST-Grep

语法树级重写

面向 25 种语言做结构化匹配和改写，适合批量重构、模式替换和代码迁移。

Hashline

拒绝改错行

每行带内容哈希，修改时必须引用稳定行标识。文件变化时验证失败，避免污染代码。

Tmux

真实终端工作区

Agent 可以跑 REPL、调试器和 TUI 工具，进程持续存在，团队成员也能被可视化观察。

MCP

外部能力接入

内置 websearch、Context7、Grep.app 等能力，并支持技能按需携带自己的 MCP 服务器。

Skills

任务级能力包

技能不仅是 Prompt，还可以包含工具、MCP、约束和工作流，只在需要时加载，保持上下文清爽。

07 / Final Summary

最后总结：OMO 的价值在哪里

第一层

它让 OpenCode 不再只是一个聊天式编码助手，而是有主控、有角色、有任务分工的团队。

第二层

它把规划、执行、验证、修复做成闭环，降低 Agent 半途而废和上下文跑偏的概率。

第三层

它用 LSP、AST-Grep、Hashline、MCP、Tmux 等工具，把 Agent 的动作落到真实工程环境里。

第四层

OMC 和 OMX 说明这套思路可以迁移到 Claude Code 和 Codex CLI，但 OMO 的重点是开放模型与 OpenCode 生态。

一句话收口

OMO 的重点不是“多叫几个 Agent”，而是把需求澄清、计划制定、专家分工、并行执行、工具调用、验证修复组织成一套能持续交付的 AI 开发团队工作流。

OMO = OpenCode + Sisyphus + Team Mode + Engineering Tools
