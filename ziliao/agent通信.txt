# AGENT 如何对接不同的消息通道

来源视频：`/Users/dds/Downloads/AGENT如何对接不同的消息通道.mp4`

## 一句话总结

AGENT 对接飞书、钉钉、企业微信等消息通道时，不应该让 AGENT 直接适配每个平台，而应该在平台和 AGENT 之间增加消息通道层：负责输入标准化、文件下载、会话排队、并发控制、输出转换和文件上传。

## 核心问题

用户通过消息通道发来的内容不只有文字，也可能是图片、视频、PDF 或其他文件。这些文件通常先存在平台自己的文件服务器上，而 AGENT 运行在另一台服务器上。

反过来，AGENT 生成的图片、表格、报告等文件，也只是 AGENT 服务器上的本地文件路径。要让用户在飞书、钉钉、企业微信中真正收到可打开的文件，就必须先上传到对应平台的文件服务，再发送平台可识别的文件标识。

## 三层设计

### 1. 消息接入层

不同平台的消息结构不一样。如果 AGENT 直接适配每个平台，平台细节会侵入 AGENT 层，通道越多维护越困难。

更合理的方式是在消息通道和 AGENT 之间增加一层抽象：

- 把飞书、钉钉、企业微信等不同来源的消息转换成统一消息格式。
- AGENT 只关心会话、消息类型和内容，不关心平台差异。
- 对文件类消息，通道层要先从平台文件服务下载到 AGENT 可访问的位置，再把本地路径或可访问 URL 交给 AGENT。

### 2. 会话队列与并发控制

消息通道通常不会限制用户连续发消息。即使 AGENT 正在处理上一条消息，用户仍然可以继续发送第二条、第三条。

因此需要两级控制：

- 同一会话内串行排队：前一条消息处理完之后，再处理下一条，保证上下文稳定。
- 不同会话之间允许并发：张三、李四、王五可以同时使用同一个机器人。
- 全局并发需要限流：不能无限放开 100 个或 1000 个并发，否则服务器可能被打满；可以设置最大并发数，超过后进入队列。

### 3. 消息输出层

AGENT 处理完成后可能产生多种输出：

- 普通文字回复
- 工具调用过程或结果
- 思考过程
- 图片、表格、报告等文件

普通文本可以通过统一的消息输出格式交给通道层，再由通道层调用飞书、钉钉、企业微信各自的 API 发送。

文件输出更复杂：AGENT 生成的是服务器本地路径，这个路径对平台和用户没有意义。通道层需要先把文件上传到平台文件服务，拿到平台返回的 file key、media id 等标识，再通过平台接口发送给用户。

另一种做法是提供专门的发送工具，例如 `send_file`、`send_image`。AGENT 决定发什么，工具和通道层负责怎么发、发到哪里。

## 推荐架构

```mermaid
flowchart LR
  User["用户"] --> Platform["飞书 / 钉钉 / 企业微信"]
  Platform --> Ingress["消息接入层"]
  Ingress --> Normalize["统一消息模型"]
  Normalize --> Queue["会话队列与并发控制"]
  Queue --> Agent["AGENT"]
  Agent --> Outbox["统一输出模型"]
  Outbox --> Egress["消息输出层"]
  Egress --> Platform

  PlatformFiles["平台文件服务"] --> Ingress
  Ingress --> LocalFiles["AGENT 可访问文件"]
  Agent --> GeneratedFiles["AGENT 生成文件"]
  GeneratedFiles --> Egress
  Egress --> PlatformFiles
```

## 分享时可强调的观点

- AGENT 层要尽量保持平台无关。
- 消息通道层负责平台适配、文件搬运和收发协议。
- 会话队列是消息通道接入里非常关键但容易忽略的部分。
- 对开发者来说，掌握这些原理层，比一开始记住每个平台的所有 API 细节更重要。
- 原理清楚后，可以先描述需求快速实现，再通过调试和优化逐步完善。
