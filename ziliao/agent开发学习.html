S05
技能

Skill Loading / 加载、暴露、调用

技能是这样被加载和使用的

启动时扫描 skills/*/SKILL.md，系统提示只放技能简介；真正要用时，模型调用 load_skill，完整技能正文才进入上下文。

关键点：技能不是预先塞满 system prompt，而是被注册成一个“可发现、可按需读取”的工具资源。

加载流程

  1. skillsDir 指向当前目录下的 skills/。
  2. NewSkillLoader 创建加载器，并立即调用 loadAll。
  3. loadAll 递归寻找所有 SKILL.md。
  4. 读取文件后解析 frontmatter，目录名就是技能名。
  5. 结果存入 map[string]Skill，后续按名称读取。
skills/ SKILL.md frontmatter skills map

使用流程

  1. GetDescriptions 生成技能列表，注入 system prompt。
  2. 模型看到“有哪些技能”，但还看不到完整正文。
  3. 任务需要专业流程时，模型发起工具调用：load_skill({"name":"weather"})。
  4. toolHandlers["load_skill"] 调用 GetContent。
  5. GetContent 返回 <skill name="...">完整正文</skill>，作为 tool result 注入。
Principle

加载阶段只建索引，使用阶段才取正文；这就是技能系统省 token 又能保持专业性的原因。

S06
压缩

Context Compact / 让长会话活下去

上下文不是仓库，是工作台

压缩机制的重点不是“少放点 token”，而是区分什么必须留在工作台上，什么只要能从档案里找回来。

Agent 做大项目时，失败通常不是因为不会推理，而是工作台被旧输出堆满，新的判断没有空间。

它解决什么问题

工具结果天然膨胀：读大文件、跑测试、看日志都会产生大量一次性信息。它们当时有用，但不应该永久占据模型注意力。

旧结果占位 阈值摘要 原文落盘

真正的机制

  1. 微压缩：旧工具结果不再保留全文，只留下“之前用过什么工具”的痕迹。
  2. 自动压缩：上下文超过阈值时，让模型把当前会话总结成连续性摘要。
  3. 手动压缩：模型意识到上下文变脏时，可主动调用 compact。
  4. 完整 transcript 先保存到磁盘，保证压缩不是不可逆删除。
Principle

压缩的本质是记忆分层：当前判断靠摘要，完整证据靠档案。

S07
任务图

Persistent Task Graph / 持久化任务图

Todo 只能记进度，任务图才能表达工作结构

任务系统的重点是把“我要做什么”从对话里拿出来，变成磁盘上可查询、可依赖、可恢复的控制平面。

当目标变复杂，关键不再是列清单，而是知道哪些事能并行，哪些事还被谁挡住。

它解决什么问题

扁平 todo 无法表达依赖。比如“写测试”要等“实现接口”，“集成”要等多个模块都完成。没有图，Agent 只能凭感觉排顺序。

节点 依赖边 状态机 磁盘真相

真正的机制

  1. 每个任务是一个 JSON 节点，持久化在 .tasks/。
  2. blockedBy 表示“我还在等谁”，blocks 表示“我会解锁谁”。
  3. 状态机控制任务生命周期：pending → in_progress → completed。
  4. 完成一个节点时，系统自动更新依赖关系，让后续节点解锁。
Principle

任务图是 Agent 的项目管理内核：它把“下一步做什么”变成一个可计算的问题。

S09
团队

Persistent Agent Team / 持久队友

子智能体是临时工，队友是有身份的长期进程

团队机制的重点不是“多开几个模型”，而是给每个模型身份、状态和通信通道，让它们能持续协作。

一旦 agent 有了名字、角色、收件箱和生命周期，它就从一次性函数调用变成团队成员。

它解决什么问题

子智能体做完就消失，无法等消息、继续上下文、承担长期角色。复杂项目需要 coder、tester、reviewer 这样的稳定分工。

名册 身份 邮箱 独立循环

真正的机制

  1. 团队名册保存在 config.json，记录成员、角色、状态。
  2. spawn 不只是调用模型，而是启动一个长期运行的 teammate loop。
  3. 通信通过 JSONL 收件箱完成：写入是发送，读取后清空是消费。
  4. 每个队友在调用模型前先检查自己的 inbox，把消息注入上下文。
Principle

团队不是并发数量，而是“身份 + 生命周期 + 消息总线”的组合。

S11
自治

Autonomous Work Claiming / 自组织工作

自治不是自由发挥，是空闲时知道去哪找活

自治机制的重点不是让模型“自己想干嘛就干嘛”，而是给它一个安全的空闲循环：看消息、扫任务、认领可做项。

领导不再逐个派工，队友进入 idle 后会主动寻找未阻塞、未认领的任务。

它解决什么问题

团队扩大后，领导逐个分配任务会成为瓶颈。任务板明明有活，但没有“自动认领”机制，队友只能被动等待。

工作态 空闲态 轮询 认领

真正的机制

  1. 队友处于 WORK 时正常处理当前任务；停止工具调用后进入 IDLE。
  2. IDLE 每隔一段时间检查 inbox，有消息就恢复工作。
  3. 没有消息时扫描任务板，找 pending、无 owner、无阻塞的任务。
  4. 认领时写入 owner，并把任务状态推进到 in_progress。
Principle

自治的关键不是更强的模型，而是一个受约束的“找活干”循环。
