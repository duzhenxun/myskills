## 一句话总结

Claude Code 的上下文管理不是简单“装满了就摘要”，而是一套分层防御系统：先用低成本规则清理，再用会话记忆提取事实，极端情况下做完整压缩，并通过自动触发与熔断机制守住系统底线。

## 核心观点

上下文窗口不是一个静态容器，而是系统里最昂贵、最稀缺的战略资源。好的上下文工程不是问“还能不能装得下”，而是持续判断“每一条数据到底该不该装进去”。

## 四层上下文防御

### L1 微压缩：低成本规则清理

- 不调用大模型，靠规则清理冗余工具结果。
- 重点清理长输出、低价值、已过期的工具结果，例如读文件、跑脚本、网页搜索等。
- 难点不是“删什么”，而是“怎么删还不破坏服务端 prompt cache”。
- 缓存还活着时走 Cached Microcompact：只让服务端移除旧工具结果，不改本地前缀。
- 缓存过期时走 Hard Microcompact：直接在本地把旧工具输出替换成短占位。
- 还要隔离主线程和子 Agent 的数据来源，避免清理到不属于当前主对话的工具结果。

### L2 会话记忆压缩：提取结构化事实

- 不做简单摘要，而是让后台 Agent 从长对话里提取结构化事实。
- 例如项目技术栈、当前进度、用户偏好、关键约束等。
- 这些事实写入类似 `Memory.md` 的长期记忆文件。
- 系统同时保留最近几轮完整对话，让模型既有长期全局信息，也有眼前细节。
- 保留窗口有三个刻度：最少 token、最少消息数、最大 token 上限。
- 回溯保留最近消息时必须遵守结构边界锁：`tool_use` 与 `tool_result` 不能拆散，同一个 message id 下的流式片段也不能切开。

### L3 完整压缩：重型降维手术

- 当会话记忆也撑不住时，系统才调用大模型做完整压缩。
- 压缩 prompt 会要求模型从多个维度复盘当前对话、用户意图、任务状态和关键上下文。
- 设计上会让模型先在临时标签里深度思考，再只保留最终摘要，避免把“草稿纸”塞回上下文。
- 如果待压缩内容本身过长，会按时间从旧记录开始丢弃、重试，最后仍不行就放弃。
- 压缩成功后还要做“战后重建”：清空当前缓存，并重新注入关键文件、计划、Skill 内容和 MCP 工具说明。

### L4 自动触发：压缩开关与熔断器

- 每次模型调用后检查当前 token 用量。
- 如果超过上下文上限减去安全缓冲区，就自动触发压缩。
- 触发顺序先走较低成本的会话记忆压缩，再走完整压缩。
- 真实生产事故里，连续自动压缩失败曾导致大量无意义 API 调用。
- 因此系统加入熔断：连续失败超过阈值后直接停止重试。
- 还要排除负责压缩的子 Agent 自己触发压缩，防止压缩 Agent 递归触发新的压缩。

## 四层之外的源头控制

### 数据指针替换

工具输出可能非常大。系统不会把大块结果直接塞进上下文，而是把真实数据放到外部存储，只在上下文里留下指针和短摘要。模型需要细节时再按指针读取。

### 渐进式工具扩展

Claude Code 内置很多工具，但不会一开始全部塞进上下文。初始只提供读写文件等核心工具；需要 MCP 或远程能力时，再按需加载更多工具说明。这样既减少 token 消耗，也降低模型选错工具和重试造成的上下文污染。

## 可演讲的收束

- 上下文不是垃圾桶，而是战略资源。
- 低成本清理优先，高成本压缩兜底。
- 结构边界比 token 数更重要。
- 压缩不是终点，压缩后的上下文重建同样关键。
- 真正成熟的上下文系统，一定包含自动触发、失败熔断和递归防御。
